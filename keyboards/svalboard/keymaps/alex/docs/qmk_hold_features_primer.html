Hold-features primer — svalboard lightly

Every feature this build can turn on, which knob actually reaches the firmware, and what to set for 42 tap-holds, two exempt thumbs, and a numpad layer you want to combo over. Companion to the hypr-chord findings.

At a glance — four gates, evaluated in order

you press a mod-tap / layer-tap
  │
  ├─ GATE 1  FLOW TAP      guards TIME    "was I just typing?"          → instant tap
  │     whitelist only: SPC A–Z . , / ;  · off while Ctrl/GUI/Alt held
  │
  ├─ GATE 2  CHORDAL HOLD  guards SPACE   "same-hand roll?"             → instant tap
  │     thumbs (matrix rows 0 and 5) are exempt — both via the row guard and via '*'
  │
  ├─ GATE 3  HOLD_ON_OTHER "another key pressed?"         → instant hold  off
  │
  └─ GATE 4  PERMISSIVE    "another key typed while held?"  → hold
        then TAPPING_TERM expires → hold if still down, tap if released

The one rule that explains almost every bug on this board: gates 1 and 2 are checked before gate 4, so a "no" from chordal or flow tap pre-empts the permissive-hold answer that would have given you a hold — but only inside tapping_term. Chordal's release branch is nested inside if (WITHIN_TAPPING_TERM(event)) (action_tapping.c:275), and the after-term path at :515 resolves the key as a hold without consulting it: hold past the term and chordal has no vote at all. Your layout is 42 tap-holds, so essentially every key you press runs this ladder.

Two consequences specific to us, developed below: the thumb is structurally the safe place for layer access (Thumbs & numpad), and combos resolve keycodes from the active layer, which is why layer-6 chords behave differently (Combos × layers).

Every alpha key on this board is a tap-hold. That is the regime where chordal hold and permissive hold disagree most, and it is why generic QMK advice ("just enable chordal hold") misfires here: chordal's premise is that most keys are plain letters, and none of yours are.

The risky pairs are same-hand centre-column neighbours — the keys your index and middle fingers share: r1c+r2c, r2c+r3c, l1c+l2c… Chordal hold reads them as typing; you mean them as chords. That single mismatch is the bug in the other report.

Pattern: the cross-hand ones are reliable, the same-hand ones only work with chordal hold off. That asymmetry is the whole diagnosis, visible straight out of the combo table.

Thumbs, and the two number layers

Layers 5 and 6 are mirrors of each other, and each puts the number block under the opposite hand from the other. Getting these two crossed is the single easiest way to misread a symptom on this board.

layerentered byleft handright handl1s is
5ltd (SPC) / rtd (ESC) numbers 1–9, 0nav: arrows, PGUP/PGDN, HOME/END, + media/brightness on row 43
6ltlo (TAB) / rtlo (APP) F1–F12numbers 1–9, 0F3

Both layers leave every thumb key TRNS, so the thumbs keep their layer-0 layer-taps while a layer is active — you can stack layer 6 on top of layer 5, and the thumb holding a layer open never stops working.

Layer 6 is the one people call "the numpad": right hand 1–9, 0, left hand F1–F12, entered from the outer-lower thumb on each side so each thumb unlocks the other hand's block. But layer 5 carries a number block too, on the left hand — so hypr+3 via l1s is a layer 5 gesture, while hypr+F3 from the same finger is layer 6.

why the thumb is the right place for layer access
  matrix row 0 = left thumb, row 5 = right thumb
  get_chordal_hold()  → row 0 or 5 → return true          guard 1
  chordal_hold_layout → '*' for rows 0 and 5              guard 3, same answer
  ⇒ a thumb is never force-tapped by a chord; it latches through permissive hold the moment you type

Thumb-first is the reliable ordering for layer+key chords — with one exception: combos match keycodes from the active layer, so a thumb layer that goes on first disables any layer-0 combo. That tension is resolved in Combos × layers.

A layer-tap can't also be a layer-lock, so this is a real choice: keep LT(6,TAB) for the fast case, and put LL(6) on a thumb key you rarely use — ltdd/rtdd (the pushthrough) are free today. Then long numbers become tap-on, type with both hands, tap-off, and the thumb is out of the chord business entirely.

Combos × layers — the trap, and two ways out

// quantum/process_keycode/process_combo.c:56
__attribute__((weak)) uint8_t combo_ref_from_layer(uint8_t layer) { return layer; }
⇒ combos match the keycode resolved from the ACTIVE layer, not the physical position

layer 0:  r1c = MT(CS|J)  r2c = MT(SG|K)   → combo[8] fires
layer 5:  r1c = DOWN      r2c = UP         → cannot fire
layer 6:  r1c = 4         r2c = 5          → cannot fire

Which thumb is which matters here: rtd = LT(5,KC_ESC) is layer 5, and layer 6 is the outer thumb rtlo/ltlo — Thumbs & the two number layers.

So "numpad + hypr chord" is impossible today in the order layer-then-chord, and only works in the order chord-then-layer. Two ways to remove the ordering constraint:

Option A — make combos position-based (one function, global effect) 
// keymap.c — this symbol is still weak, so it is safe to override here
uint8_t combo_ref_from_layer(uint8_t layer) {
    return 0;   // combos always read the layer-0 binding of the physical key
}

All 50 combos become position chords: they fire from the same two keys under layer 6, 5, whatever. Numpad digits still come from layer 6, so hypr + 4 + 5 → HYPR + digits in any order.

Cost, and it is real: a combo trigger key is held in the combo buffer for combo_term before being released. Pinning combos to layer 0 extends that buffering to the numpad digits that sit at trigger positions. With combo_term 60 that is a 60 ms lag on those digits — measure before committing, and consider just set 2 40 alongside it.

Option B — duplicate the chord on the numpad layer (surgical) 
combo[8]   MT(CS|J) + MT(SG|K)  → MT(HYPR|0xD1)   layer 0, unchanged
combo[42]  KC_4       + KC_5     → MT(HYPR|0xD1)   fires on layer 6, same two positions

No global change, no new latency anywhere else, and you keep 50 slots (28 in use). Cost is bookkeeping — each chord you want under a layer needs a twin, and the twins are keyed on keycodes, so they break if you rebind layer 6.

Recommendation: B for the two or three chords you actually use with the numpad. Reach for A only if you find yourself wanting chords over most layers.

Making the chord itself reliable (five separate knobs) 
the gate people miss: a tap-hold's keycode reaches process_combo only when the tap-hold resolves
press of a tap-hold → process_tapping swallows it (action_tapping.c:245, returns true, no process_record)
tick events at 1 kHz (keyboard.c:580) → a still-held key resolves as HOLD at press_time + TAPPING_TERM
⇒ two fingers pressed `skew` apart reach the combo matcher `skew` apart

process_combo.c:481   if (timer && timer_elapsed(timer) > time) { DISABLE_COMBO(combo); }
process_combo.c:621   timer = timer_read();   // reset on every combo-key press
⇒ skew > combo_term (60 ms) disables the combo outright
⇒ earliest possible fire = tapping_term + combo_term ≈ 260 ms
  1. Widen combo_term — QSID 2, 60 → 100–120. The only runtime lever on the gate above. It is a deadline, not a delay: releasing a trigger applies the prepared combo immediately, so you never wait the term out, and a fast typed pair can never chord because a tap delivers press+release atomically. Two clocks ↓
  2. Chordal hold pre-empts permissive hold at release time (action_tapping.c:316 beats :339) → a quick same-hand chord is force-tapped into j + k instead of resolving as two holds. Hold past the term and it works; release early and it doesn't. Either QSID 26 off, or the MT+MT guard in the other report. Note the press-time force-tap at :424 is skipped for MT+MT — is_tap_record() is true for mod-taps and layer-taps.
  3. Both keys must stay down until the combo fires. A trigger released before the combo resolves takes the "released key was part of an incomplete combo" path and the chord dies.
  4. Keep a third finger off the neighbours. overlaps() (process_combo.c:402) drops the shorter of any two combos that share even one trigger. combo[20] = r1c+r2c+r3c → BTN1 and combo[21] = +r4c → BTN2 share both of combo[8]'s triggers, so a resting ring finger turns your HYPR chord into a mouse click before any timing question is even asked.
  5. COMBO_MUST_HOLD_PER_COMBO is not compiled in, so get_combo_must_hold() doesn't exist in this build. Add the define to builddefs/build_vial.mk if you want "only fire if both still held at the deadline" — that is the single best misfire guard for tap-hold-triggered combos.

get_combo_term() currently ignores index, so a per-combo term set in Vial is silently discarded — fix that before trying to widen only the same-hand chords.

Compile-time — the four edits that actually change behaviour

  1. Guard same-hand tap-hold chords in get_chordal_hold() — MT+MT → true. Keeps gate 2 for tap-hold + plain letter, which is what typing actually looks like. diff
  2. Make get_combo_term() honour index, then widen the same-hand combos (the global bump in the table above does the same thing bluntly, from EEPROM, no reflash): 
    uint16_t get_combo_term(uint16_t index, combo_t *combo) {
    switch (combo->keycodes[0]) {
        case MT(MOD_LCTL | MOD_LSFT, KC_J):   /* combo[8] hypr */
        case MT(MOD_LSFT | MOD_LGUI, KC_K):   /* combo[4]  */
            return 120;
    }
    return QS.combo_term;
}
  3. Right-thumb flow tap — add case LT(5, KC_ESC): beside LT(5, KC_SPC), and drop the stray { after case LSFT_T(KC_M):.
  4. Numpad latch — put LL(6) on a pushthrough thumb key so long entries don't need a held thumb. LAYER_LOCK_ENABLE = yes is already in the build.

And the unglamorous winner: for anything you need under time pressure, put the finished chord on the layer instead of asking four gates to agree. C_S_A_G(KC_3) on layer 5 turns "hypr + rtd + l1s" into thumb + one key; same trick with C_S_A_G(KC_F3) on layer 6. No gate in this document can touch either — but pick a cell that is empty on that layer rather than overwriting the plain 3 / F3.

Shape of a per-key rule, once you're inside qmk_settings.c 
bool get_permissive_hold(uint16_t keycode, keyrecord_t *record) {
    // today: `return QS_tapping_permissive_hold;`  (one global bit)
    // per-key: keep the global as the default, carve out exceptions
    if (IS_QK_LAYER_TAP(keycode)) return true;   // thumbs + layer keys always chord
    return QS_tapping_permissive_hold;
}

Same shape works for get_tapping_term — e.g. a shorter term on the bottom-row single-mod keys (C·Z, G·X, A·C, S·V, S·M) which you tap constantly, and a longer one on the three-mod keys where a mistimed tap is the most expensive.
