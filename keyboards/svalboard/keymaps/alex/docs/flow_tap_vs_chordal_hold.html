Chordal hold does not make combo[8] impossible — it makes it late and fragile. A tap-hold's keycode only reaches the combo matcher when the tap-hold resolves; the press itself is swallowed. Two independent requirements, which is why it feels unreliable: land the two fingers within combo_term of each other (a chord, not a roll) and keep both down past tapping_term (so each resolves as a hold rather than a tap). Mechanics — summary, then drill down

press a tap-hold
  ├─ Flow Tap      guards TIME   "pressed right after I typed?"      → instant tap
  ├─ Chordal Hold  guards SPACE  "same-hand roll?"                   → tap, at release
  ├─ Permissive Hold the fallback  "another key typed while held?"     → hold
  └─ COMBO TERM     guards ARRIVAL "did both triggers land in 60 ms?"   → disable combo

order is the whole story: chordal is evaluated before permissive, so a chordal "false"
pre-empts the answer that would have given you a hold. And because a tap-hold's keycode only exists for the
combo matcher after resolution, the combo gate is measured against resolution times, not finger times.
Chordal hold guard order — and why the thumb is already exempt 
get_chordal_hold(a, b)                        // quantum/qmk_settings.c:341

  GUARD 2  both are mod-tap/layer-tap ....... return true   ← proposed patch, finger↔finger only
  GUARD 3  get_chordal_hold_default() ....... other=='*' || hand != other_hand

r1c + r2c   → GUARD 1 misses → GUARD 2 would catch it; today falls to GUARD 3 → 'R'=='R' → false

GUARD 2 does nothing for the thumb. Its only effect is finger↔finger same-hand chords — exactly the failing half. Note is_mt_or_lt() is static in action_tapping.c:69, so it must be spelled IS_QK_MOD_TAP(x) || IS_QK_LAYER_TAP(x).

The gate that decides it: combos see resolved keycodes, not presses 
1. the press is swallowed
   action_tapping.c:245   press of a tap-hold → tapping_key = *keyp; return true
                          // process_record() is never called → process_combo never sees it

2. a held key resolves on its own clock
   keyboard.c:580         generate_tick_event() → action_exec(MAKE_TICK_EVENT)  // 1 kHz
   action_tapping.c:514   after TAPPING_TERM, tap.count == 0 → process_record(&tapping_key)  // HOLD
   ⇒ the hold's press reaches process_combo at  press_time + TAPPING_TERM
   ⇒ two keys pressed `skew` apart resolve      `skew` apart

3. the combo matcher then applies its own deadline
   process_combo.c:481    if (timer && timer_elapsed(timer) > time) { DISABLE_COMBO(combo); }
   process_combo.c:621    timer = timer_read();   // reset on every combo-key press, not STRICT
   ⇒ when the second trigger arrives, elapsed == the press skew
   ⇒ skew > combo_term (60 ms) → the combo is disabled outright

4. and when it does fire, j and k are swallowed, not typed
   process_combo.c:377    earlier trigger records → TICK_EVENT   // discarded
   process_combo.c:366    last trigger record → rewritten to combo->keycode

This is the model that fits both of your observations. Earliest possible fire is tapping_term + combo_term ≈ 260 ms after the first press — that is the threshold you found. Below it, the outcome is decided by which release branch runs; above it, by whether the two fingers landed within 60 ms.

One consequence worth knowing: while a combo is pending, the trigger events sit in key_buffer and nothing is emitted until the combo resolves or the buffer is dumped. So the whole chord feels delayed by roughly that window, and a raised combo_term buys the skew window with added lag on every combo trigger key — all of which are tap-holds on this board.

The two choke points (and a correction about the first) 
inside `if (tapping_key.tap.count == 0)` the branches are tried in this order:
  :282  own-key release                → first tap
  :316  chordal  "Chord considered a tap"        ← pre-empts
  :339  permissive "No tap. Interfered by typing" → hold

press-time (:424)  the force-tap is guarded by `if (!is_tap_record(keyp))`, and
                     is_tap_action() returns true for MT and LT (action.c:1162)
                     → skipped for MT+MT. My earlier claim that it fired here was wrong.
                     Its only other effect, `tap.interrupted = false`, is read only under
                     HOLD_ON_OTHER_KEY_PRESS (action.c:516) — a no-op at our settings.
release-time (:316) this is the one that bites: press r1c, press r2c, release inside
                     TAPPING_TERM → waiting_buffer_typed() is true → force-taps the pair → j + k.
Outcome matrix — chordal on vs off

So chordal hold's real cost here is one row: it converts the quick chord — the one that should be the easiest — from a hold into a tap. Board B's permissive-hold branch rescues it because that branch emits the whole burst in a single matrix scan, so the two triggers land ~0 ms apart.

Making get_chordal_hold() return true for MT+MT doesn't "make it a hold" — it stops chordal pre-empting permissive hold, which then does its normal job.

Gate 0 nobody thinks about: overlaps() steals the shorter chord

// and it is applied the moment a longer combo becomes fully pressed (:494)
if ((drop = overlaps(buffered_combo, combo))) DISABLE_COMBO(drop);

Consequence for you: combo[20] shares both of combo[8]'s triggers and has one more key, so if your ring finger is resting on r3c when the chord resolves, combo[8] is disabled and you get BTN1 — a mouse click — where you wanted HYPR. Add r4c and you get a right-click. Same for combo[4] (shares r2c), combo[9] and combo[19] (shares r2c with it as well), which overlap on a single key and therefore also drop the 2-key chord.

This is a finger-placement failure mode, not a timing one — which fits "sometimes it works, sometimes it doesn't, on the same keyboard" better than timing alone. It is also testable in one repro: chord r1c+r2c with the ring finger deliberately held on r3c and see whether you click instead of mod.

Four gates stacked, and gate 4 is measured from delivery 
r1c↓  becomes tapping_key, not delivered downstream
r2c↓  MT+MT → press-time force-tap skipped → both queued, invisible to process_combo
rtd↓  row 5 → GUARD 1 → true → queued, settles nothing

gate 0 OVERLAP          — is r3c/r4c also down? → combo[8] dropped, you get BTN1/BTN2
gate 1 TAPPING_TERM 200 ms — nothing reaches the combo matcher until a key resolves
gate 2 CHORDAL :316        — release one early → j + k (or a hold, depending on which key you let go)
gate 3 COMBO_TERM 60 ms    — both presses must land within 60 ms of each other's delivery
gate 4 the result is MT(CSAG|BTN1) — keep holding or you left-clicked

The 60 ms window is measured from when the tap machine hands the key over, not from when your finger moved. That is why "press them together" feels like it shouldn't fail and does.

Gate 2's outcome is not always j + k. If the first key had already resolved as a hold, releasing the second one gives you a lone mod — which is precisely the shift+GUI + 3 you are seeing: the layer and the digit arrived fine, only HYPR did not.

Fixes, ranked

Ranked by how directly each one moves the gate that decides this gesture — resolution skew < combo_term, with both keys held past tapping_term. The first two are runtime, EEPROM-persisted, and reversible in seconds.

  1. Widen the arrival window. just py-set 2 120 — combo_term 60 → 120. This is the only runtime dial that acts on the gate that is actually failing you. Try it before touching anything else; it also helps combo[4], combo[3], combo[7], combo[26], which are the other same-hand chords.
  2. Decide what chordal hold is buying you. Its measured cost is one row of the matrix: a quick same-hand chord becomes a tap instead of a hold. Board B proves the gesture wants it off — just py-set 26 0 on A and live with it for a week before writing C.
  3. Best structural fix: stop routing this through a chord — but not on l1s. For hypr + 3 the obvious move is C_S_A_G(KC_3) at layer 5 / l1s, but that cell is your 3, and a 5-digit modded keycode is unconditional — you would lose plain 3 on layer 5. Same trap on layer 6 / l1s, which is your F3. Use a cell that is empty on that layer instead: l4e is the candidate on both, but it was not captured in the saved fingerprint, so verify with just layer-cell 4 1 before overwriting anything. One key, chordal-exempt thumb, no combo, no 260 ms, no overlap risk.
  4. Watch finger placement while chording. A resting finger on r3c completes combo[20], which shares both triggers and is longer, so overlaps() disables combo[8] and you get a mouse click instead of HYPR. Free, and it may be a bigger share of your "random" failures than the timing is (Combo).
  5. Targeted patch: GUARD 2. Keeps typing protection, restores MT+MT chords by stopping chordal pre-empting permissive hold. diff ↓
  6. Ordering discipline — combo first, layer last, land the fingers together, and hold past ~260 ms before releasing either one. Free; do it now (The gesture).
  7. Per-combo terms, once get_combo_term() honours index — today it returns the global for every combo, so a per-combo term set in Vial is discarded. Then widen only the same-hand chords instead of everything. -DCOMBO_TERM_PER_COMBO is already on.
  8. Rebalance flow tap whichever way you go (Dials) — with chordal off it is your only net.

Corrections made during this investigation

Both of these were wrong in the first version of this report, and the second one only got caught because your observation contradicted it. Keeping them visible so the correction isn't quietly re-lost:

  1. "Chordal hold force-taps r1c the moment r2c is pressed" — false. The press-time branch is guarded by !is_tap_record(keyp), which is false for mod-taps and layer-taps. The force-tap is at release (:316) and only inside the tapping term.
  2. "The two triggers are never down at once, so combo[8] cannot fire" — too strong. They can both resolve as holds, and the combo does fire, about tapping_term + combo_term after the first press. What chordal hold actually costs is the quick chord, and the real binding constraint is press skew vs combo_term — which is why just py-set 2 120 now leads Fixes.
