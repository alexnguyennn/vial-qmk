L1 · why exactly these four pads

L2 · the four links, opened on demand

L1 · the pad matrix has no boot baseline — keyboards/svalboard/matrix.c

Pads are plain digital reads with a per-column polarity fixed at compile time (config.h:50): MATRIX_COL_PUSHED_STATES { 0, 0, 1, 0, 0, 0 } — note col 2 is inverted.

matrix.c:168  // "The first scan comes out backwards for reasons we don't understand.
              //  Skipping it, stops the lockup experienced with thumbs out on board boot."
              if (first_scan) { memset(raw_matrix, 0, sizeof(raw_matrix)); ... }

matrix.c:103  // DD (push-through) pad: sample its boot state, XOR it out forever after
              scans_before_dd_detect = 3;  ...  dd_detected = pin_state;  pin_state ^= dd_detected;

Two workarounds already exist for pads that are in the wrong state at power-on — the maintainers know. But first_scan discards one scan, and the DD trick covers one pad. Default debounce is sym_defer_g @ DEBOUNCE 5, so anything still read as touched 5 ms after boot becomes a genuine press event.

L2 · resting pads complete a combo instead of a keystroke 
$ just svalboard flow-status   →   combo_term 60 · tapping_term 220 · flow_tap 100 · permissive_hold 1 · chordal_hold 0

Every rested pad flips in the same matrix scan, so QMK receives them as one burst — combo_term never comes into play, they are simply simultaneous. Per hand, the first two centre pads complete #7/#8 immediately.

L4 · a combo can only be released by its own input keys 
/* quantum/process_keycode/process_combo.c:540-570 — the ONLY caller of release_combo() */

No release event for the chord keys ⇒ combo->active stays set ⇒ the output's release is never generated. clear_combos() deliberately skips active combos, so nothing else heals it. That is the entire "must trigger the combos to get back to neutral" ritual — and why it is needed once per hand: two independently latched combos.

Where the inference is

Links 2, 3 and 4 are verified facts about this board (live keymap, live combo table, source). The inferred part is why the pads stay pressed after the fingers leave: most likely the pad's sense baseline is established with a finger on it, so the 1→0 transition the combo needs never happens. A press-then-release of the pair manufactures exactly that transition — which is what you observe. The boot trace in prove it settles it.

Userland only — no core firmware edits

Answer to "can we do this without touching core firmware?": yes, almost all of it. The keymap is compiled into the same binary, and QMK's earliest user hook runs before combos: pre_process_record_quantum() → pre_process_record_kb/user() → process_combo() (quantum.c:286-289). So a keymap can veto a combo press that the core code would otherwise act on.

A · Vial config only — makes the latch impossible (no rebuild, no flash of code)

combo #7   out: MT(CSAG|BSLS)     →  OSMT(MOD_HYPR, KC_BSLS)   ← hyper applies to next key, self-clears
combo #8   out: MT(CSAG|MS_BTN1)  →  OSM(MOD_HYPR)             ← its tap was broken anyway (see note)
combo #20/#21 out: KC_MS_BTN1/2   →  leave, or delete; B stops them arming at boot
  • One-shot mods are cleared by QMK itself on the next key, so a boot-time firing is a non-event.
  • Verify after editing: just svalboard layer-combos — OSMT lives at 0x6000+ and the decoder prints raw hex there; that's expected, not an error.
  • Why #8's tap was already dead: MT(mod, KC_MS_BTN1) puts the mouse-keycode range value (0x00D1) into the tap slot, which is sent as a raw HID usage rather than going through mousekey handling. Only the hold ever worked.

B · keymap.c boot grace — the load-bearing ~15 lines

/* keymaps/alex/keymap.c — next to the other user hooks */
#define BOOT_GRACE_MS 400
static uint16_t boot_grace_t0;
static bool     boot_grace_done;

bool pre_process_record_user(uint16_t keycode, keyrecord_t *record) {
    if (boot_grace_done) return true;
    if (!boot_grace_t0) boot_grace_t0 = timer_read();
    if (timer_elapsed(boot_grace_t0) < BOOT_GRACE_MS) return false;  /* swallow: no combo, no tap-hold */
    boot_grace_done = true;
    clear_keyboard();   /* drop anything the boot burst already registered */
    return true;
}
  • Returning false here is earlier than process_combo(), earlier than the tapping state machine, and earlier than process_record_kb() in keymap_support.c.
  • The stray release that arrives when you finally lift a phantom pad is harmless: mod-tap release with nothing registered = del_mods() no-op; combos fall into their "incomplete combo" branch and pass it through.
  • Cost: the first ~400 ms after plug-in is ignored, and a pad that was rested at boot still needs one lift before its next press registers — that behaviour is identical to the core fix D, because in both cases the pad is treated as already-released.

C · keymap.c escape hatch — one press instead of the both-hands ritual

/* keymap.c — this fork has no QK_CLEAR_KEYBOARD, so expose clear_keyboard() yourself */
enum { SV_PANIC_NEUTRAL = QK_KB_0 + 21 };        /* next free slot after SV_QMK_STATE_TOGGLE (0x7E14) */

case SV_PANIC_NEUTRAL:
    if (record->event.pressed) clear_keyboard();  /* quantum/action.h:124 */
    return false;
/* vial.json → "customKeycodes": append as the 22nd entry (index 21 → 0x7E15 = 32277) */
{ "name": "SV_PANIC_NEUTRAL", "shortName": "Panic\nNeutral", "title": "clear_keyboard(): drops stuck mods/keys." }
/* optional self-healing net — append inside the existing housekeeping_task_user() */
static uint16_t last_event_ms;                     /* set in post_process_record_user(): */
/*     last_event_ms = timer_read();                                                              */

if (get_mods() && last_event_ms && timer_elapsed(last_event_ms) > 2000) {
    clear_keyboard();
    last_event_ms = timer_read();                  /* fire once, not every scan */
}

Caveat: holding a mod with zero other key events for >2 s looks identical to the bug, so it will be cleared. If that annoys you, keep only the panic key — or gate on get_oneshot_mods()==0 && get_mods()==MOD_HYPR to target the actual signature.

D · only if you want the phantom pads gone (core)

/* keyboards/svalboard/matrix.c — generalise the existing dd_detected trick to all pads */
if (boot_baseline_open) {                       /* after the existing first_scan block */
    if (!boot_baseline_t0) boot_baseline_t0 = timer_read();
    if (timer_elapsed(boot_baseline_t0) < 250) {
        for (uint8_t r = 0; r < ROWS_PER_HAND; r++) boot_baseline[r] |= curr_matrix[r];
        memset(raw_matrix, 0, sizeof(raw_matrix)); return true;
    }
    boot_baseline_open = false;
}
for (uint8_t r = 0; r < ROWS_PER_HAND; r++) {
    boot_baseline[r] &= curr_matrix[r];     /* pad seen released → drop its mask */
    curr_matrix[r]  &= ~boot_baseline[r];   /* pad still held from boot → invisible */
}

Why B can't do this part: userland can veto events, not the cooked matrix state. Anything that reads the matrix directly — keymap_support.c's mouse_keys_pressed bookkeeping, debug_matrix, auto-mouse — still sees phantom pads. That's the residual, and it is also why the auto-mouse layer churns at boot.

Free falsification test

The bug should also appear on silent re-boots while your hands are on the board: OS_DETECTION_KEYBOARD_RESET (config.h:107) and SPLIT_WATCHDOG_ENABLE (:84) reset the MCU without touching a cable — KVM switch, host sleep/wake, OS switch. If it genuinely never appears except at plug-in, link 1 goes back on the table.
