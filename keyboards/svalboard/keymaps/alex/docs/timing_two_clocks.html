Two clocks — combo_term vs tapping_term

Answers to two sharp questions about the hypr-chord report. Both of its premises were worth checking, and one of them caught a real error in that report. Sources: quantum/action_tapping.c, quantum/process_keycode/process_combo.c.

Q1 — does combo_term 120 mean I hold longer to register hypr+3?

✓
No — on the path you actually use. combo_term is a deadline, not a delay. Releasing any trigger key flushes the prepared combo immediately; you never wait the term out. 
// process_combo.c:634 — the tail of process_combo(), runs on EVERY event
if (record->event.pressed && is_combo_key) {
    timer = timer_read();
    key_buffer[...] = record;            // press of a trigger: buffer it, wait
} else {
    if (combo_buffer_read != combo_buffer_write) {
        apply_combos();                  ← RELEASE of a trigger fires the combo NOW
    } else { dump_key_buffer(); }
}

// the ONLY thing that waits for combo_term is combo_task():
if (timer && timer_elapsed(timer) > longest_term) { apply_combos(); }   ← fires if you keep holding

So there are two ways the chord lands, and they race:

you…the chord fires…so combo_term 60 → 120…
release either triggerthat instantno change at all
keep holding bothafter combo_term from the last trigger landing60 ms later

And it never touches the hold duration you are actually fighting. How long you must keep both keys down is set by tapping_term — each trigger has to resolve as a hold before the combo matcher can see it at all, and that is 200 ms per key, untouched by QSID 2.

The one thing that is gated by combo_term 
// process_combo.c:481 — checked the instant the SECOND trigger's press is delivered
if (timer && timer_elapsed(timer) > time) { DISABLE_COMBO(combo); return; }

// and :621 resets the timer on every combo-key press, so at that moment:
elapsed == the gap between the two triggers' deliveries == your finger skew

This is the only thing raising the number buys you: two triggers may land up to combo_term apart instead of 60 ms apart. A chord your fingers delivered 90 ms apart is dead at 60 and alive at 120. It is a tolerance dial, not a speed dial.

Q2 — doesn't the diagram show chordal always winning? I'd get j/k every time

✗
The diagram was wrong and your reading of it is right. Chordal hold is not a gate that runs before the others — it is a branch that lives inside the within-tapping-term block, so it literally cannot run once the term expires. 
// action_tapping.c, the structure that decides everything here

284      own-key release              → tap          // :284  "First tap(0->1)"

     }
515  else {   // AFTER TAPPING_TERM

519          process_record(&tapping_key);       → HOLD.  chordal is never consulted.

Therefore: hold both keys past tapping_term and get_chordal_hold() is never called for that resolution — board A and board B behave identically. That is exactly why you are not always getting j/k, and why "hold past a threshold and it works" works on the chordal-on board too.

Within the term, two more things come before chordal, which is why the failure is subtler than "chordal wins":

Which means the A↔B difference is narrower than "chordal on = j/k": it shows up for the release-the-second-key-first ordering. The other early-release ordering loses on both boards. That is a correction to the outcome matrix in the main report.

Why a typed "jk" can never chord, at any combo_term 
tap resolution delivers press and release back to back:
  r1c tap  → process_combo sees MT(CS|J) press, then release → KEY_STATE_UP clears bit 0
  r2c tap  → process_combo sees MT(SG|K) press → ALL_COMBO_KEYS_ARE_DOWN? bit 0 already up → no

⇒ a combo only ever forms between two keys that are simultaneously HELD down as holds.
⇒ raising combo_term does not turn fast typing into chords on this board, because every
   trigger in the 50-slot table is a mod-tap or layer-tap.

Net: on a board where every combo trigger is a tap-hold, this dial is close to free. My original framing — "costs latency on every combo trigger key" — overstated it, and "the only runtime dial that acts on the gate" understated how narrow that gate is: it is finger skew, and only for chords that are held long enough to resolve as holds in the first place.

Recipe, in the order that matches the two clocks

1  just py-set 2 120          combo_term — widens finger-skew tolerance. free-ish.
2  just py-set 26 0           chordal off — only affects the :316 ordering, inside the term.
3  technique: press both, keep both down past ~200 ms, then release.
       release is what fires it — you are not waiting for a timer.
4  if it still misfires, it is not timing: it is overlap theft
       (ring finger on r3c completes combo[20] → BTN1 instead of HYPR).

What to watch for, because it separates the remaining hypotheses cleanly: a stray mouse click means overlap theft or a too-early release of the MT(CSAG|BTN1) result; j and k mean you released inside the term; a lone shift+GUI means the second key resolved as a hold and the first did not; and shift+GUI+3 means all of that plus layer 5 already on (l1s = 3 on layer 5).

Still the cleanest fix for anything you need under time pressure: put the finished chord (C_S_A_G(KC_3)) on a cell that is empty on that layer, so no clock is involved at all.
